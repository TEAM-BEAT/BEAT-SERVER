# BEAT 예매 구조 점검 및 개선 작업 보고서

- 작성일: 2026-08-03
- 범위: 비지정 좌석 예매, 재고 차감, 입금 확인, 취소·환불, 알림
- 목적: 현재 구조의 적합성을 평가하고 구현 우선순위를 확정한다.

## 1. 결론

현재 BEAT에는 **회차 Row 비관적 락을 유지하는 것이 가장 적합하다.**

조건부 원자적 UPDATE가 단순 재고 카운터에는 더 가볍지만, BEAT는 재고 외에도 회차 상태와 예매 마감 시각을 확인하고 예약을 함께 생성한다. 현재 트래픽에서 락 경합 문제가 측정되지 않았고, 기존 방식은 동작과 실패 지점을 이해하기 쉽다. 이력서를 위해 원자적 UPDATE로 바꾸는 것은 권장하지 않는다.

다만 현재 구조가 완성형인 것은 아니다. 락 방식 교체보다 다음 세 가지가 정합성에 더 중요하다.

1. 서버에서 구매 수량을 **요청당 1~10매**로 검증한다.
2. 네트워크 재시도로 같은 구매가 두 번 생성되지 않도록 **멱등성**을 보장한다.
3. 결제 완료·환불 요청 상태의 예약이 일반 취소로 재고를 반환하지 못하도록 **상태 전이 규칙**을 강화한다.

## 2. 확정된 정책

| 항목 | 정책 |
|---|---|
| 좌석 유형 | 비지정 좌석 |
| 구매 제한 | 한 번의 구매 요청당 최대 10매 |
| 추가 구매 | 허용 |
| 사용자·회차별 누적 구매 한도 | 없음 |
| 동일 사용자의 동일 회차 복수 예약 | 허용 |
| 재고 기준 | 회차별 전체 좌석 수와 누적 판매량 |

따라서 `UNIQUE(user_id, schedule_id)` 같은 제약은 추가하면 안 된다. 정상적인 추가 구매까지 막기 때문이다.

클라이언트의 10매 제한은 사용자 경험을 위한 1차 검증일 뿐이다. API는 직접 호출할 수 있으므로 서버가 최종적으로 동일한 제한을 검증해야 한다.

### 클라이언트 구현 교차 검증

2026-08-03 기준 [BEAT-Client `develop` 브랜치](https://github.com/TEAM-BEAT/BEAT-Client/tree/develop)를 확인했다.

| 확인 항목 | 클라이언트 구현 | 판단 |
|---|---|---|
| 요청당 수량 | [`Count.tsx`](https://github.com/TEAM-BEAT/BEAT-Client/blob/develop/src/pages/book/components/count/Count.tsx)에서 `Stepper max={10}` 사용 | 요청당 최대 10매 정책과 일치 |
| 최소 수량 | [`Stepper.tsx`](https://github.com/TEAM-BEAT/BEAT-Client/blob/develop/src/components/commons/stepper/Stepper.tsx)에서 1매일 때 감소 버튼 비활성화 | 최소 1매 정책과 일치 |
| 추가 구매 | [`Book.tsx`](https://github.com/TEAM-BEAT/BEAT-Client/blob/develop/src/pages/book/Book.tsx)는 이전 구매량을 조회하거나 합산하지 않고 구매 시도마다 새 예약 요청 | 사용자·회차별 누적 한도가 없다는 정책과 일치 |
| 결제 완료 취소 | [`Cancel.tsx`](https://github.com/TEAM-BEAT/BEAT-Client/blob/develop/src/pages/cancel/Cancel.tsx)와 [`useCancelBooking.tsx`](https://github.com/TEAM-BEAT/BEAT-Client/blob/develop/src/hooks/useCancelBooking.tsx)는 결제 완료 예약에 환불 계좌를 받고 환불 API 호출 | 일반 취소와 환불을 구분하려는 정책과 일치 |
| 중복 제출 UI | 제출 버튼은 회원 또는 비회원 mutation이 pending이면 비활성화 | UX 방어는 있으나 네트워크 재전송·타임아웃 재시도를 막지 못함 |
| 멱등성 키 | 예약 API 요청에 멱등성 헤더 또는 키가 없음 | 서버와 클라이언트 모두 추가 필요 |

클라이언트 구현은 정책 의도를 확인하는 자료이지 정합성의 최종 방어선은 아니다. 수량, 가격, 예약 상태, 취소 가능 여부는 서버가 다시 계산하고 검증해야 한다.

추가로 발견된 계약 불일치가 있다. 클라이언트는 `CHECKING_PAYMENT` 상태에서도 사용자가 “입금했어요”를 선택하면 환불 API를 호출한다. 현재 서버 도메인은 `BOOKING_CONFIRMED` 상태에서만 환불 요청을 허용한다. 따라서 **송금은 완료됐지만 운영자가 아직 입금을 확인하지 않은 시간대**에 환불 요청이 실패할 수 있다. 이 경우의 정책을 확정하고 양쪽 구현을 맞춰야 한다.

## 3. 현재 구조 평가

### 잘 설계된 부분

- 회차 한 건을 PK로 잠가 같은 회차의 재고 변경을 직렬화한다.
- 재고 변경과 예약 생성을 같은 MySQL 트랜잭션에서 처리한다.
- 락을 획득한 뒤 DB 시각으로 예매 마감을 다시 판단한다.
- 여러 예약을 처리하는 관리 기능은 ID를 정렬해 잠금 순서를 맞춘다.
- 예약 생성 이벤트는 커밋 이후에 처리해 외부 알림 실패가 예약 트랜잭션을 롤백시키지 않는다.
- 예약 시점의 결제 금액을 저장해 이후 가격 변경의 영향을 받지 않는다.

예매 마감 판단의 상세 근거는 [예매 마감 처리 ADR](./booking-close-processing-adr.md)을 따른다.

### 보완이 필요한 부분

| 위험 | 현재 상태 | 영향 |
|---|---|---|
| 최대 구매 수량 | 서버는 양수 여부만 확인 | API 직접 호출로 10매 초과 구매 가능 |
| 중복 요청 | 예약 생성 멱등성 장치 없음 | 타임아웃·재시도 시 중복 예약 가능 |
| 취소·환불 상태 전이 | 서버의 일반 취소 범위가 넓고, 입금 확인 전 환불 요청은 클라이언트와 서버 규칙이 다름 | 잘못된 재고 반환 또는 사용자의 정상 환불 요청 실패 가능 |
| 미입금 만료 | 명시적인 만료 상태와 반환 작업 없음 | 미입금 예약이 재고를 장기간 점유할 가능성 |
| 게스트 비밀번호 암호화 | 회차 락 보유 중 수행 | 불필요하게 락 점유 시간이 늘어남 |
| 결제·환불 감사 정보 | 상태와 처리 이력 부족 | 운영자가 변경 사유와 처리자를 추적하기 어려움 |
| 알림 내구성 | 일부 알림이 프로세스 메모리 실행에 의존 | 서버 종료·스레드풀 포화 시 유실 가능 |

## 4. 락 방식 결정

### 지금은 비관적 락을 유지한다

현재 흐름은 다음과 같다.

```text
트랜잭션 시작
→ 회차 Row 비관적 락
→ DB 시각 기준 마감 확인
→ 잔여 좌석 확인 및 차감
→ 예약 저장
→ 커밋
→ Slack 등 후속 처리
```

Slack 이벤트에 누적 판매량과 전체 좌석 수가 필요한 것은 원자적 UPDATE를 배제할 이유는 아니다. UPDATE 후 같은 트랜잭션에서 회차를 다시 조회할 수 있다. 그러나 조회 한 번을 줄이거나 늘리는 문제보다 **락을 얼마나 오래 보유하는지, 상태 판단을 어디에서 하는지, 중복 요청을 어떻게 막는지**가 더 중요하다.

### 원자적 UPDATE는 측정 후 검토한다

다음 조건이 실제 지표로 확인될 때 별도 ADR에서 전환을 검토한다.

- 인기 회차에서 락 대기 시간이 서비스 목표를 지속적으로 초과한다.
- DB 처리량의 병목이 회차 조회와 재고 차감 경로로 확인된다.
- 재고 조건을 한 SQL에 넣어도 마감·상태 규칙이 명확하게 유지된다.
- 변경 전후 동시성 테스트에서 처리량과 지연 시간이 유의미하게 개선된다.

전환 후보 쿼리는 다음 형태지만 지금 바로 적용할 작업은 아니다.

```sql
UPDATE performance_schedule
SET sold_ticket_count = sold_ticket_count + :quantity
WHERE id = :scheduleId
  AND sold_ticket_count + :quantity <= total_ticket_count
  AND booking_close_at > CURRENT_TIMESTAMP(6);
```

이 방식을 사용하더라도 예약 저장까지 같은 트랜잭션에 포함하고, 영향받은 행이 0건일 때 마감·재고 부족 등을 구분하는 정책이 필요하다.

### 지금 도입하지 않을 방식

- 낙관적 락: 인기 회차처럼 충돌이 집중되는 경우 재시도가 늘어난다.
- 애플리케이션 `synchronized`: 서버가 여러 대면 인스턴스 사이의 동시성을 막지 못한다.
- Redis 분산 락: 데이터 원장은 MySQL인데 별도 장애 지점과 운영 복잡도만 추가될 수 있다.
- 대기열·예약 홀드 시스템: 지정 좌석, PG 결제, 대규모 티켓 오픈이 필요해질 때 검토한다.

## 5. 구현 작업

### P0 — 출시 정합성

#### A. 서버의 요청당 구매 수량을 1~10매로 제한

작업:

- 요청 DTO와 도메인 생성 로직 모두에서 `1 <= purchaseTicketCount <= 10`을 검증한다.
- 초과 요청에 사용할 명확한 에러 코드와 메시지를 추가한다.
- 가능하면 DB에도 `CHECK (purchase_ticket_count BETWEEN 1 AND 10)`을 추가해 방어 계층을 만든다.
- 클라이언트의 `max={10}`은 유지하되 서버 에러 코드에 맞는 안내를 표시한다.

완료 조건:

- 0매, 음수, 11매 이상 요청이 예약 생성 전에 거절된다.
- 1매와 10매 요청은 성공한다.
- 같은 사용자가 10매 구매 후 별도의 요청으로 추가 구매할 수 있다.

#### B. 취소·환불 상태 전이 보호

작업:

- 일반 취소가 가능한 상태를 도메인에 명시한다.
- 결제 완료 예약은 일반 취소 대신 환불 요청 경로만 사용한다.
- 환불 요청 중인 예약은 일반 취소로 재고를 반환하지 못하게 한다.
- 무료 공연 예약의 최초 상태와 취소 규칙을 명시한다.
- `CHECKING_PAYMENT` 상태에서 사용자가 이미 송금했다고 신고한 경우의 처리 정책을 확정한다.
- 확정한 상태 전이와 클라이언트의 일반 취소·환불 API 분기를 동일하게 맞춘다.

권장 상태 규칙:

```text
입금 대기 + 미송금 → 일반 취소 가능
입금 대기 + 송금 신고 → 환불 요청 또는 입금 확인 대기 정책 필요
결제 완료 → 환불 요청만 가능
환불 요청 → 관리자 환불 완료/거절만 가능
취소·환불 완료·만료 → 재고 반환은 정확히 한 번만 수행
```

권장안은 `CHECKING_PAYMENT`에서도 환불 계좌가 포함된 요청이면 `REFUND_REQUESTED`로 전환하되 재고는 유지하는 것이다. 관리자가 실제 입금을 확인한 뒤 환불 완료 또는 거절을 처리한다. 사용자의 송금 여부만 믿고 즉시 취소하거나 재고를 반환해서는 안 된다.

완료 조건:

- 결제 완료·환불 요청 예약에 일반 취소 API를 호출하면 거절된다.
- 입금 확인 전 송금 신고에 대한 클라이언트와 서버 응답이 일치한다.
- 어떤 경로에서도 동일 예약의 재고가 두 번 반환되지 않는다.
- 상태별 허용·거절 전이가 단위 테스트로 고정된다.

#### C. 예약 생성 멱등성 보장

멱등성은 사용자당 구매 횟수를 제한하는 기능이 아니다. **동일한 한 번의 구매 요청이 네트워크 문제로 반복 전달됐을 때 중복 실행을 막는 기능**이다. 사용자가 추가 구매를 누르면 새로운 키를 사용하므로 정상적으로 별도 예약이 생성된다.

작업:

- 클라이언트가 구매 시도마다 `Idempotency-Key`를 생성해 전송한다.
- 사용자가 확인 버튼을 누른 순간 키를 만들고, 동일 구매 시도의 재시도에는 같은 키를 재사용한다.
- 서버는 사용자와 멱등성 키의 조합을 DB UNIQUE 제약으로 보호한다.
- 같은 키와 같은 요청이면 기존 결과를 반환한다.
- 같은 키로 수량·회차가 다른 요청이 오면 충돌 오류를 반환한다. 이를 위해 요청 지문을 함께 저장한다.
- 성공 결과뿐 아니라 처리 중·실패 상태의 재호출 정책을 정의한다.

권장 제약:

```text
UNIQUE(user_id, idempotency_key)
```

게스트 식별 방식이 회원과 다르면 게스트용 안정적인 요청 주체 식별자를 별도로 설계한다.

완료 조건:

- 동일 키 요청을 동시에 여러 번 보내도 예약과 재고 차감은 한 번만 발생한다.
- 서로 다른 키를 사용하면 같은 사용자·회차의 추가 구매가 허용된다.
- 같은 키로 다른 요청 본문을 보내면 기존 결과를 재사용하지 않고 오류로 처리한다.
- 클라이언트의 pending 버튼 비활성화도 유지하고, 요청 함수 내부 조건은 회원·비회원 중 하나라도 pending이면 차단하도록 통일한다.

### P1 — 운영 안정성

#### D. 미입금 예약 만료 정책 도입

먼저 기획에서 입금 대기 시간을 확정해야 한다. 임의의 만료 시간을 구현하지 않는다.

작업:

- `payment_due_at`과 `EXPIRED` 상태를 추가한다.
- 만료된 입금 대기 예약을 배치가 찾아 재고를 반환한다.
- 배치도 기존과 동일하게 회차 → 예약 순서로 잠근다.
- 결제 확인과 만료 작업이 동시에 실행되는 경합 테스트를 작성한다.

완료 조건:

- 결제 확인과 만료 중 하나만 성공한다.
- 만료 재실행에도 재고가 중복 반환되지 않는다.

#### E. 비관적 락 임계 구간 축소

작업:

- 게스트 비밀번호 해시처럼 회차 상태와 무관한 CPU 작업을 회차 락 획득 전으로 이동한다.
- Slack, SMS, 외부 API 호출은 트랜잭션 밖에서 수행한다.
- 트랜잭션 내부에는 DB 정합성에 필요한 조회와 저장만 둔다.

완료 조건:

- 회차 락을 보유한 구간에 비밀번호 해시와 외부 호출이 없다.
- 변경 전후 락 보유 시간과 API 지연을 측정한다.

#### F. 타임아웃·재시도 정책 정리

작업:

- 애플리케이션 트랜잭션 타임아웃, DB lock wait timeout, API 타임아웃의 관계를 문서화한다.
- 데드락과 일시적 lock timeout만 짧고 제한적으로 재시도한다.
- 재고 부족, 마감, 검증 실패 같은 비즈니스 오류는 재시도하지 않는다.
- 재시도되는 예약 생성에는 반드시 같은 멱등성 키를 사용한다.

완료 조건:

- 재시도 대상 예외가 코드에 명시돼 있다.
- 최대 횟수와 backoff가 제한돼 있다.
- API 타임아웃 후 백그라운드에서 예약이 성공하더라도 재호출로 중복 예약되지 않는다.

### P2 — 운영 성숙도와 성능

#### G. 결제·환불 감사 이력 강화

- 결제 확인·환불 요청·환불 완료·거절 상태를 구분한다.
- 처리 시각, 처리자, 사유를 기록한다.
- 운영자 변경 API에는 중복 실행 방지용 요청 식별자를 둔다.

#### H. 관리자 결제 확인의 불필요한 회차 락 검토

결제 확인 자체가 재고를 변경하지 않는다면 회차 락이 필요한지 테스트와 상태 전이 규칙을 기준으로 검토한다. 삭제·취소·환불처럼 재고를 반환하는 작업은 회차 락을 유지한다.

#### I. 중요 알림의 내구성 확보

Slack이 단순 운영 알림이면 현재 커밋 후 비동기로 충분할 수 있다. 고객 SMS처럼 반드시 전달돼야 하는 메시지는 DB Job Queue 또는 Transactional Outbox를 적용한다. 상세 설계는 [입금 확인 및 SMS 비동기 처리 제안](./ticket-payment-confirmation-outbox-sqs.md)을 따른다.

#### J. 동시성 부하 테스트와 관측 지표 추가

측정 항목:

- 회차 락 대기 시간 p50/p95/p99
- 회차 락 보유 시간 p50/p95/p99
- 예약 API 지연과 타임아웃 비율
- 데드락·lock timeout 횟수
- 재고 부족 실패율과 성공 처리량
- 중복 요청 탐지 횟수
- 실제 재고와 활성 예약 수량의 불일치 여부

테스트 시나리오:

- 한 회차의 마지막 좌석에 동시 요청 집중
- 10매 요청 다수와 잔여 좌석 부족 경쟁
- 예매 마감 직전에 락 대기가 발생하는 상황
- 동일 멱등성 키의 동시 재전송
- 서로 다른 키를 사용한 동일 사용자의 추가 구매
- 결제 확인과 취소·만료의 동시 실행

원자적 UPDATE는 이 결과에서 현재 방식이 목표를 충족하지 못할 때 비교 실험한다.

## 6. 권장 작업 순서

```text
1. 구매 수량 1~10 서버 검증
2. 취소·환불 상태 전이 차단
3. 예약 생성 멱등성
4. 미입금 만료 정책 확정 및 구현
5. 비관적 락 임계 구간 축소
6. 타임아웃·재시도·관측 지표 정리
7. 결제·환불 감사 이력과 중요 알림 내구성 강화
8. 부하 테스트 후 락 방식 재평가
```

1~3은 재고 성능 최적화보다 먼저 처리해야 하는 정합성 작업이다. 4는 입금 대기 시간에 대한 기획 결정이 선행돼야 한다. 8의 측정 결과가 나쁘지 않다면 비관적 락을 계속 사용해도 된다.

## 7. 목표 예매 흐름

```text
요청 수신
→ 사용자 인증 및 요청당 1~10매 검증
→ 멱등성 키 등록 또는 기존 처리 결과 확인
→ 트랜잭션 시작
→ 회차 Row 비관적 락
→ DB 시각 기준 마감·판매 상태 확인
→ 잔여 좌석 확인 및 차감
→ 예약과 결제 기한 저장
→ 멱등성 처리 결과 저장
→ 커밋
→ Slack·SMS 등 후속 작업 발행
```

같은 사용자의 추가 구매는 새로운 멱등성 키로 위 흐름을 다시 수행한다. 사용자·회차별 누적 구매량을 계산하거나 제한하지 않는다.

## 8. 최종 판단

BEAT의 현재 비관적 락 기반 재고 처리는 규모와 도메인 복잡도를 고려하면 합리적이다. 개선의 중심은 락 기술을 바꾸는 것이 아니라 **서버 검증, 상태 전이, 멱등성, 만료와 운영 관측**을 완성하는 데 있다.

따라서 현재 구조를 다음과 같이 정의한다.

> 회차 단위 비관적 락으로 재고와 예약의 정합성을 우선 보장하고, 요청 멱등성과 명시적인 결제·취소 상태 전이로 중복 처리와 잘못된 재고 반환을 차단한다. 원자적 UPDATE는 실제 락 경합이 확인될 때 적용할 수 있는 성능 최적화 후보로 유지한다.
